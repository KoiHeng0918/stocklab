# stocklab：同一扣库存请求，五种并发控制策略的对照实验

一个最小业务（4 个接口、2 张表）的并发控制实验项目。

同一个 `POST /order/create` 请求，分别用 5 种扣库存策略执行，观察两件事：

1. **正确性**：高并发下会不会超卖、库存会不会变成负数；
2. **性能**：在都不超卖的前提下，吞吐和延迟的代价差多少。

目标不是做商城，而是把「下单扣库存」这个场景里的丢失更新、条件更新、乐观锁、悲观锁讲清楚，并用可复现的数据比较。

---

## 1. 业务范围

业务刻意封版，只有 4 个业务接口 + 1 个压测辅助接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/order/create?requestId=xxx&skuId=1` | 创建订单并扣库存 |
| GET | `/order/{requestId}` | 按幂等键查订单 |
| POST | `/order/{id}/cancel` | 取消订单并回滚库存 |
| GET | `/stock/getStock/{skuId}` | 查询库存 |
| GET | `/benchmark/retry-count` | 仅压测用：读取 E2 重试次数 |

数据只有两张表：

- `stock`：单 SKU 库存，`sku_id` 固定为 1；
- `orders`：订单，`request_id` 上有唯一索引 `uk_request_id`。

订单状态只有：

```text
0 = CREATED
2 = CANCELLED
```

没有 `PAID`，也不做支付、优惠券、分布式事务等与实验无关的功能。

## 2. 实验矩阵

| 组 | 扣减方式 | 预期结果 |
|---|---|---|
| **E0** | 先 `SELECT stock`，再 `UPDATE stock = #{stock-1}` | 丢失更新，订单数 > 库存 |
| **E0b** | 无条件 `UPDATE stock = stock - 1` | 没有下限保护，库存变负数 |
| **E1** | 条件更新 `UPDATE ... WHERE stock >= 1` | 不超卖，基线方案 |
| **E2** | 读 `version`，CAS `UPDATE ... WHERE version = ? AND stock >= 1`，失败重试 | 不超卖，但高并发下重试容易耗尽 |
| **E3** | `SELECT ... FOR UPDATE` 后扣减 | 不超卖，锁等待明显 |

E0 / E0b 是**故意写错**的对照组，用来证明「看起来能跑」的写法为什么错；它们不是候选方案。

策略通过 `benchmark.strategy` 配置切换：

```yaml
benchmark:
  strategy: e1
```

可选值：`e0`、`e0b`、`e1`、`e2`、`e3`。

> 切换后必须重启应用。策略 Bean 由 `@ConditionalOnProperty` 在启动时装配，运行中改配置不会生效。

## 5. 核心实现

### 5.1 策略模式切换实验组

```java
public interface StockDeductStrategy {
    boolean deduct(Long skuId);
}
```

每个实验组一个实现类，用 `@ConditionalOnProperty` 控制只装配一个 Bean。

### 5.2 事务边界

扣库存和写订单放在 `OrderCreateTransactionService.createInTransaction` 中：

```text
扣库存 → 写订单 → 提交
```

单独抽一个 Bean，是为了让 `OrderServiceImpl` 能在事务**外面**捕获 `DuplicateKeyException`，以及为 E2 的每次重试开启新事务。

### 5.3 幂等

三层保证：

1. 进入事务前先按 `request_id` 查一次；
2. 插入订单时 `uk_request_id` 唯一索引兜底；
3. 捕获 `DuplicateKeyException` 后回查赢家订单，直接返回。

唯一索引是最终保证，前两步只是减少无谓的插入。

### 5.4 取消订单

```sql
UPDATE orders SET status = 2 WHERE id = ? AND status = 0
```

- 更新到 1 行：订单状态从 CREATED 变成 CANCELLED，同一事务内 `stock = stock + 1`；
- 更新到 0 行：说明已被并发取消，直接返回当前订单，保证幂等。

### 5.5 E2 的重试位置

E2 的 CAS 失败不 `sleep` 重试，而是抛出 `VersionConflictException`，由 `OrderServiceImpl` 在外层重新调用事务方法。

原因：MySQL 默认 REPEATABLE READ，如果在同一个事务里重试，第二次读到的还是同一个快照，版本冲突永远不会消失。每次重试必须是新事务。

### 5.6 业务错误与系统错误分开

| 状态码 | 含义 |
|---|---|
| 400 | 参数校验失败 |
| 404 | 订单或库存不存在 |
| 409 | 业务失败：库存不足、版本冲突重试耗尽 |
| 500 | 系统错误：连接池耗尽、超时、数据库异常 |

压测时不能只看 JMeter 的 `Error%`：409 是实验预期的业务失败，必须按 `responseCode` 分开统计。

## 6. 正确性结果

**负载**：库存 1000，200 线程 × 25 循环 = 5000 请求。

**环境**：远程 MySQL 8.0.46 + SSH 隧道（这一阶段只关心最终数据，绝对延迟不作为性能结论）。

超卖定义：

```text
超卖 = max(0, 成功订单数 - 初始库存)
```

| 组 | 订单数 | 剩余库存 | 超卖 | 200 | 409 | 500 | Error% | 吞吐 | P95 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| E0 | 4588 | 897 | **3588** | 4588 | 0 | 412 | 8.24% | 6.0/s | 49372 ms |
| E0b | 4823 | **-3823** | **3823** | 4823 | 0 | 177 | 3.54% | 5.4/s | 52928 ms |
| E1 | 1000 | 0 | **0** | 1000 | 3923 | 77 | 80.00% | 12.9/s | 38638 ms |
| E2 | 304 | 696 | **0** | 301 | 4626 | 73 | 93.98% | 6.5/s | 49135 ms |
| E3 | 1000 | 0 | **0** | 1000 | 3832 | 168 | 80.00% | 9.3/s | 62036 ms |

读表要点：

- **E0**：只有 897 次扣减真正落库，却生成了 4588 张订单，丢失更新 3588 次；`stock` 还是正数，所以只看「库存有没有小于 0」发现不了问题。
- **E0b**：没有下限判断，库存直接扣成负数，负多少就等于超卖多少。
- **E1 / E3**：各卖出准确的 1000 单，库存归零，超卖 0。
- **E2**：只卖出 304 单，但库存还剩 696，超卖仍是 0。409 主要是**版本冲突重试耗尽**，不是库存不足。
- E2 的数据库订单数 304 与 HTTP 200 数 301 差 3：有 3 个请求已提交事务，但客户端收到 500/超时。以数据库为准。
- 表中的 500 是连接池/隧道等系统错误，不是业务失败；它们不应被算进「超卖」结论。

E0b 的订单数和库存数在不同运行之间会波动（另一次是 4893 / -3893），因为它本身没有并发控制；结论「库存为负」不变。

## 7. 性能结果

**环境**：本机 MySQL 5.7.27，应用与数据库同机。

**负载**：库存 100000，线程 50 / 100 / 200 / 500，每组 50 循环，重复 3 次。每组开始前重置库存和订单。

### 7.1 E1：条件更新（基线）

| 线程 | 吞吐 r1 / r2 / r3 | 中位吞吐 | P95 r1 / r2 / r3 |
|---:|---|---:|---|
| 50 | 1911 / 1748 / 1891 /s | 1891/s | 46 / 52 / 49 ms |
| 100 | 1885 / 2071 / 2153 /s | 2071/s | 99 / 94 / 113 ms |
| 200 | 2010 / 2129 / 2041 /s | 2041/s | 210 / 197 / 236 ms |
| 500 | 2394 / 1433 / 1045 /s | 1433/s | 339 / 573 / 680 ms |

观察：

- 50～200 线程吞吐都在 2000/s 左右，说明服务端存在上限（Hikari 50 个连接 × 单事务耗时），继续加线程只会增加排队延迟；
- 500 线程的三次差异较大（2394 → 1433 → 1045），最可能是 MySQL 在持续写入后内部状态变化（undo / 刷盘），不是代码逻辑变化。这一组后续取中位数，并在结论里注明方差。

### 7.2 E2：乐观锁 + 重试

| 线程 | 成功 QPS r1 / r2 / r3 | 409 比例 | P95 r1 / r2 / r3 |
|---:|---|---:|---|
| 50 | 113 / 86 / 97 /s | 86.0% / 93.8% / 93.8% | 62 / 40 / 34 ms |
| 100 | 103 / 120 / 122 /s | 94.0% / 93.9% / 93.9% | 75 / 68 / 68 ms |
| 200 | 130 / 126 / 131 /s | 93.8% / 94.0% / 94.0% | 170 / 168 / 165 ms |
| 500 | 135 / 119 / 133 /s | 94.1% / 94.1% / 94.1% | 294 / 329 / 299 ms |

E2 性能矩阵（127500 请求）期间，应用重启后的真实重试统计：

```text
重试次数：247530
总请求：127500
成功请求（HTTP 200）：7846
成功率：6.15%
每请求平均重试：1.94 次
每成功请求平均重试：31.5 次
理论上限：127500 × 2 = 255000 次
```

结论：

- E2 在 100 线程以上的 HTTP 总吞吐约 1700～2300/s，但 **94% 是 409**，有效成功 QPS 只有 100～135/s；
- 库存 100000 根本没用完，409 不是库存不足，而是 `MAX_RETRY = 3` 在高并发下不够用；
- 这说明「乐观锁 + 少量重试」并不能直接用于热点行：重试预算、退避、队列或库存分片必须一起考虑。

### 7.3 E3：悲观锁

| 线程 | 吞吐 r1 / r2 / r3 | 中位吞吐 | P95 r1 / r2 / r3 |
|---:|---|---:|---|
| 50 | 1438 / 1366 / 1596 /s | 1438/s | 45 / 67 / 48 ms |
| 100 | 1424 / 1640 / 1430 /s | 1430/s | 112 / 119 / 134 ms |
| 200 | 1549 / 1704 / 1617 /s | 1617/s | 258 / 251 / 280 ms |
| 500 | 1889 / 1205 / 898 /s | 1205/s | 443 / 685 / 796 ms |

全部请求都是 200，没有 409 / 500；t500 结束后库存 25000、version 0，符合 `100000 - 75000`。

> 50 线程第一次运行时应用刚重启，首轮 598/s 是 JIT 冷启动；该轮已重跑，表中是热态 3 次数据。

与 E1 对比：

| 线程 | E1 中位吞吐 | E3 中位吞吐 | E1 P95 | E3 P95 |
|---:|---:|---:|---:|---:|
| 50 | 1891/s | 1438/s | 49 ms | 48 ms |
| 100 | 2071/s | 1430/s | 99 ms | 119 ms |
| 200 | 2041/s | 1617/s | 210 ms | 258 ms |
| 500 | 1433/s | 1205/s | 573 ms | 685 ms |

E3 的代价：

- `SELECT ... FOR UPDATE` 比 E1 多一次数据库往返；
- 行锁从 SELECT 一直持有到事务提交，持锁时间更长；
- 50～200 线程吞吐明显低于 E1，P95 更高；
- 500 线程同样出现三次递减（1889 → 1205 → 898），和 E1 的 2394 → 1433 → 1045 是同一现象：MySQL 持续写入后的状态变化，不是锁策略本身。

### 7.4 E0 / E0b：错误但更快

| 组 | 50 线程 | 100 线程 | 200 线程 | 500 线程 | P95（50/100/200/500） |
|---|---:|---:|---:|---:|---|
| E0 | 1494/s | 2218/s | 2481/s | 2593/s | 39 / 83 / 169 / 336 ms |
| E0b | 1408/s | 2227/s | 2393/s | 1482/s | 60 / 79 / 208 / 608 ms |

两组的所有请求都是 200，没有 409 / 500。

结论：

- E0 的 UPDATE 没有 `stock >= 1` 条件，E0b 连 Java 层的库存判断都没有，所以它们经常比 E1 还快；
- 但 E0 会丢失更新（订单数 > 库存），E0b 会把库存扣成负数；
- 性能高不代表方案对，这正是对照组存在的意义。

> E0/E0b 切换策略后应用重启，50 线程第一轮包含 JIT 冷启动；表中取 3 次中位数。500 线程的方差同样较大，比较时优先看趋势，不要抠单次绝对值。

### 7.5 五组放在一起

| 组 | 正确性 | 50 | 100 | 200 | 500 |
|---|---|---:|---:|---:|---:|
| E0 | 超卖 3588 | 1494/s | 2218/s | 2481/s | 2593/s |
| E0b | 库存 -3823 | 1408/s | 2227/s | 2393/s | 1482/s |
| E1 | 正确 | 1891/s | 2071/s | 2041/s | 1433/s |
| E2 | 正确，但成功率 6.15% | 成功 QPS 86–113 | 103–122 | 126–131 | 119–135 |
| E3 | 正确 | 1438/s | 1430/s | 1617/s | 1205/s |

一句话总结：

- 想又快又对，E1 在 50～200 线程下最均衡；
- E3 用吞吐和延迟换取更长的持锁时间，正确但更慢；
- E2 的乐观锁在热点行上被重试预算拖垮；
- E0/E0b 更快，但它们的「快」建立在错误结果上。

## 8. 如何复现

### 8.1 正确性

```sql
USE stocklab;
UPDATE stock SET total = 1000, stock = 1000, version = 0 WHERE sku_id = 1;
TRUNCATE TABLE orders;
```

JMeter：200 线程 × 25 循环，`requestId` 用 UUID，`skuId = 1`。

### 8.2 性能

```sql
USE stocklab;
UPDATE stock SET total = 100000, stock = 100000, version = 0 WHERE sku_id = 1;
TRUNCATE TABLE orders;
```

JMeter：线程 50 / 100 / 200 / 500，每组 50 循环，重复 3 次；每组开始前重置。

### 8.3 统计口径

- 用 `responseCode` 分组统计 200 / 409 / 500；
- 409 是业务失败，不要直接当作系统错误；
- 成功 QPS = 200 请求数 ÷ 实际耗时；
- 原始 JTL 保留在本地 `results/`，该目录已被 `.gitignore` 忽略。

### 8.4 自动化测试

集成测试位于 `src/test/java/com/stocklab/benchmark/`，使用真实 MySQL，不是 mock：

| 测试类 | 用例 | 断言 |
|---|---|---|
| `OrderIdempotencyTest` | 顺序重复 requestId | 同一订单、库存只扣 1 次 |
| | 并发重复 requestId（16 线程） | 唯一索引兜底，只有 1 张订单、库存只扣 1 次 |
| | 顺序重复取消 | 状态 2，库存只回滚 1 次 |
| | 并发重复取消（16 线程） | 条件更新只成功一次，库存只回滚 1 次 |
| | 库存不足 | `BusinessException` 状态 409，无订单残留 |
| `OrderApiTest` | 订单 / 库存不存在 | HTTP 404 |
| | 缺少 requestId / skuId = 0 | HTTP 400 |

说明：

- 测试用 `sku_id = 2` 和 `request_id` 前缀 `test-`，不碰 E0～E3 的 `sku_id = 1` 数据；
- 并发用例用 `CountDownLatch` 让线程同时起跑，验证的是数据库唯一索引和条件更新，不是 mock；
- 运行方式：IDEA 直接运行测试类，或配置 Maven 后执行 `mvn test`；
- 测试依赖本机 MySQL，需要先有可用的 `application.yml` 和 `stocklab` 库。

## 9. 已知限制

1. **单行热点是故意的**：所有请求都打 `sku_id = 1`，用来放大锁竞争；真实系统通常会做库存分片，结论不能直接外推。
2. **正确性和性能不是同一套环境**：正确性用远程 MySQL 8.0.46 + SSH 隧道，性能用本机 MySQL 5.7.27。相对结论可用，绝对 QPS 不要跨环境比较。
3. **Hikari 连接池固定 50**：500 线程测到的是「连接池 + 排队」的综合延迟，不是纯数据库延迟。
4. **E2 的成功率低是实验结论，不是隐藏 bug**：`MAX_RETRY = 3` 在热点行上不够；提高重试次数或加退避会改变性能和成功率的取舍。
5. **正确性阶段的 500 不代表业务失败**：连接池/隧道问题已被单独归类，不参与超卖判断。
6. **E0 / E0b 是反面教材**：它们只用于证明问题，不能用于生产。
